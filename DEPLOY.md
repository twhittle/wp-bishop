# Deployment and hosting notes

## What is actually live

**bishopandadkins.com runs on WordPress.** The static HTML in this repository is
**not** deployed and is not what visitors see.

This repo is the design reference: a 15-page static build of the redesign,
generated by `build.py`, intended to be rebuilt as WordPress pages (see the
Elementor/Jupiter X widget mapping in `README.md`). Treat it as a mockup and a
spec, not as a deliverable that ships.

The practical consequence: **changing a file here changes nothing on the live
site.** There is no automatic deployment, no build step on the server, and no
connection between GitHub and the host. Live content is edited in the WordPress
admin.

## Certificates

AutoSSL issues a certificate with one entry per hostname (apex, `www`, `mail`,
and so on). It is not a wildcard, so any subdomain added later must exist in
cPanel and pass its own validation; nothing is covered automatically.

To issue or re-issue: cPanel → **SSL/TLS Status** → tick the domains → **Run
AutoSSL**. Verify in a fresh incognito window, because Chrome caches
certificate errors aggressively and will keep showing a stale warning.

### The `.well-known` rule — do not remove it

The live `.htaccess` contains this line, and it needs to stay:

```apache
RewriteRule ^\.well-known/ - [L]
```

AutoSSL proves domain ownership by fetching a file under `/.well-known/` over
plain HTTP. If a redirect rule catches that request and sends it to HTTPS on a
hostname whose certificate has not been issued yet, the handshake fails and the
certificate never issues — a deadlock that blocked `www` until this line was
added.

It must sit **above** any redirect rules. WordPress rewrites its own `.htaccess`
in some circumstances (permalink changes, certain plugins), so if a future
renewal fails, check that this line still exists before investigating anything
else.

## Editing live content

All content changes happen in the WordPress admin. A few things that have
already bitten:

### Pasted URLs from Google products

A link copied out of Google Docs, Gmail, or a Google search result is usually
wrapped:

```
https://www.google.com/url?q=https://buy.stripe.com/XXXX&sa=D&source=docs
```

Used as-is, Google serves an interstitial "Redirect Notice" page before the real
destination. On a payment page this reads as a phishing warning at the exact
moment a client is about to enter card details.

The real address is the part after `q=` and before the next `&`. Paste suspect
URLs through a plain text editor first. If a URL contains `google.com/url?q=`,
it is wrapped.

This affected the Stripe payment link and has been corrected in WordPress.

## The `/2026/` preview path — needs checking

The static build was originally uploaded to `bishopandadkins.com/2026/` as a
preview. **Whether that folder still exists on the server is unverified.**

If it is still there, it is publicly reachable and indexable — a second copy of
the firm's site competing with the real one in search results, showing
placeholder testimonials and dead buttons.

Check the document root for a `2026` folder in File Manager. If present, delete
it, and add a redirect to the live `.htaccess` so any shared or indexed links
still resolve:

```apache
RewriteRule ^2026/?$ / [R=301,L]
RewriteRule ^2026/(.+)$ /$1 [R=301,L]
```

Place these below the `.well-known` line and above WordPress's own rewrite
block.

## `.htaccess` in this repo is not the live one

The `.htaccess` file in this repository was written for a static site served
from the document root. It is **not** installed on the server and must not be
uploaded as-is — it has no WordPress rewrite rules, so doing so would break
every permalink on the site.

It is kept only as a reference for the `/2026/` redirects and the `.well-known`
rule above. Borrow lines from it; do not copy the file.
